# Паутина (pautina.top)

Фронтенд платформы для хранения сертификатов, проектов и достижений. Идея была простая: у каждого человека есть публичная страница-портфолио, где лежат его документы, работы и стек технологий, а компании могут публиковать мероприятия и находить людей.

**Статус: проект закрыт и больше не развивается.** Это был MVP, сделанный чтобы проверить идею и собрать рабочий прототип. Сайт pautina.top больше не работает, а бэкенд (REST API) был в отдельном репозитории, здесь только клиентская часть. Код оставлен как архив и пример реализации.

## Что было реализовано

**Профиль и портфолио**
- у каждого пользователя своя страница, а также поддомен вида `username.pautina.top`, который через middleware отдает профиль
- профиль можно сделать приватным одним переключателем
- загрузка и кадрирование аватара, редактирование контактов и информации о себе
- светлая и темная тема, адаптив под мобильные

**Документы и сертификаты**
- загрузка файлов, предпросмотр первой страницы PDF прямо в карточке
- теги, статусы, скачивание, редактирование, удаление с подтверждением
- распознавание документа на стороне бэкенда (у пользователя ограниченное число попыток)

**Проекты и задачи**
- карточки проектов с галереей (фото и видео) и стеком технологий
- задачи с собственными галереями
- каталог стеков, которым управляет администратор

**Лента и общение**
- лента постов с бесконечной прокруткой
- комментарии, лайки, эмодзи, markdown в тексте
- мероприятия: компания создает событие, редактирует его и ведет список своих событий

**Регистрация и вход**
- пошаговая регистрация: имя, почта, код из письма, пароль, чем занимается человек (школа, вуз, работа), город, откуда узнал о проекте
- вход по паролю или по одноразовому коду
- роли: гость, пользователь, компания, администратор, для каждой есть свой guard на страницах

**Подписки**
- карточка тарифа с прогресс-баром оставшихся дней, статусом и автоплатежом
- если бэкенд возвращает флаг `offer_subscription`, клиент сам показывает предложение оформить подписку

**Админка** (`/admin`)
- дашборд со статистикой и графиками
- пользователи, документы, стеки и логи с фильтрами и пагинацией
- режим техработ: флаг лежит в Upstash Redis, при его включении все страницы отдают заглушку

## Архитектура

Код разложен по методологии Feature-Sliced Design. Страницы лежат в `src/app` (роутинг Next.js), а вся логика разнесена по слоям, и каждый слой импортирует только те, что ниже:

```
src/
  app/        страницы и роутинг
  widgets/    крупные блоки страниц (шапка, лента, профиль, сайдбар админки)
  features/   пользовательские сценарии (загрузка документа, лайк, фильтры, OTP)
  entities/   бизнес-сущности (пользователь, документ, проект, задача, тег)
  shared/     UI-кит, хуки, утилиты, цвета, типографика, API-клиент
  proxy.ts    middleware: поддомены профилей и режим техработ
```

Несколько решений, которые стоит знать:

- **Поддомены.** `proxy.ts` смотрит на хост запроса. Если это не основной домен и не зарезервированный поддомен (`blog`, `event`, `company`), то запрос на корень переписывается на `/profile/<поддомен>`, а остальные пути редиректятся на основной домен.
- **API-клиент.** Все запросы идут через `$fetch` из `shared/api`. Он сам подставляет токен, показывает тост с сообщением от бэкенда и ловит флаг про подписку.
- **Guards.** Доступ к страницам ограничивается обертками `CheckUser`, `CheckGuest`, `CheckCompany`, `CheckAdmin`.
- **Контекст пользователя.** Текущий пользователь и его права хранятся в `UserContext` и доступны во всем приложении.

## Запуск локально

Бэкенд больше недоступен, поэтому без собственной реализации API проект полностью не заработает: можно поднять только интерфейс и посмотреть на верстку. Нужны Node.js 20 и npm.

```bash
git clone https://github.com/n3side/pautina_frontend.git
cd pautina_frontend
npm ci
```

Создай файл `.env.local`:

```env
NEXT_PUBLIC_ROOT_PROTOCOL=http
NEXT_PUBLIC_ROOT_DOMAIN=pautina.test
NEXT_PUBLIC_ROOT_BACKEND=http://localhost:8000/api/
APP_ENV=local
UPSTASH_REDIS_REST_URL=
UPSTASH_REDIS_REST_TOKEN=
```

Значения выше только пример. Адрес бэкенда нужен с завершающим слэшем, потому что маршруты просто дописываются в конец. Redis нужен только для проверки техработ и работает в production-режиме.

Дальше:

```bash
npm run dev      # режим разработки
npm run build    # production-сборка
npm run start    # запуск собранного приложения
npm run lint     # проверка eslint
```

Чтобы проверять поддомены профилей локально, добавь в `hosts` записи для `pautina.test` и `*.pautina.test` (в `next.config.ts` эти origins уже разрешены).

## Деплой

Деплой был полностью автоматическим, при пуше в ветку `main` срабатывал GitHub Actions:

1. собирался Docker-образ (многоступенчатый `_docker/app/Dockerfile` на `node:20-alpine`, вывод Next в режиме `standalone`)
2. образ публиковался в GitHub Container Registry
3. на VPS по SSH копировался `docker-compose.yml`
4. на сервере подтягивался свежий образ и контейнер перезапускался

Вся тяжелая сборка происходила в CI, а не на сервере. Переменные окружения передавались в сборку через секреты репозитория, там же лежали адреса и доступы к серверу.

В папке `_docker/nginx` лежит конфиг nginx для раздачи загруженных файлов из `/storage/` с CORS и лимитом на размер тела запроса 20 МБ.

## Итоги

До полноценного продукта проект не дошел. Остались недоделанными блоки лендинга ("миссия" и "функционал"), оплата подписок и тесты. Зато за время работы получился живой MVP с регистрацией, профилями, документами, проектами, лентой, мероприятиями и админкой, а также отлаженный процесс деплоя через Docker и GitHub Actions.
